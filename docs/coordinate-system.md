# Coordinate system

This engine speaks glTF 2.0's native right-handed (RH) coordinate system end
to end — server simulation, wire format, .glb assets, sidecar files, and the
client renderer all agree. A small per-game opt-in adapter (`legacyCoordSystem`)
lets games shipped with Spring's older left-handed (LH) Lua scripts keep
working without per-script edits while the rest of the pipeline stays
RH-native.

The full migration history lives in
[`PLAN-coordinate-system.md`](../PLAN-coordinate-system.md). This doc is
the user-facing reference for game authors and tool writers who need to
know what coords flow where.

## The convention

- `+X` right, `+Y` up, `−Z` forward. Cross product is right-handed.
- Triangle winding is counter-clockwise as viewed from the front (glTF default).
- A unit at `heading = 0` faces `−Z`. Positive heading rotates `+X` toward
  `−Z` (CCW as viewed from `+Y`).
- Quaternions follow standard RH math; Babylon's
  `Quaternion.RotationYawPitchRoll` / `Quaternion.RotationAxis` work without
  sign flips once `scene.useRightHandedSystem = true`.

Every layer adopts this convention internally:

| Layer                         | Convention | Notes                                                          |
| ----------------------------- | ---------- | -------------------------------------------------------------- |
| `.glb` files on disk          | RH         | Spec-compliant. Loads in Blender, gltf-viewer, etc.            |
| Server sim (`spring-server`)  | RH         | `frontdir`, `rightdir`, `updir` form an RH basis.              |
| Wire protocol (FlatBuffers + custom binary) | RH | `pos.z` is glTF-style forward-negative.    |
| Client renderer (Babylon)     | RH         | `scene.useRightHandedSystem = true` on every scene.            |
| Sidecar files (`.config.lua` / `.config.json` / `.meta.lua`) | RH | `configVersion = 5+`. |
| Lua API surface (default)     | RH         | `Spring.GetUnitDirection` / `Spring.GetVectorFromHeading` etc. |

## `legacyCoordSystem` — the per-game opt-in bridge

Spring-derived games (Zero-K, Balanced Annihilation, …) ship with widgets
and gadgets authored against the legacy LH convention: `heading = 0`
meant `+Z`, `lwheel.offset.z` is positive for the left wheel, etc. Porting
every script by hand isn't feasible, so we run those scripts through a
runtime adapter.

### Opting in

Add one field to the game's `modinfo.lua`:

```lua
return {
    name = "Zero-K",
    shortname = "ZK",
    ...
    legacyCoordSystem = true,   -- ships with LH-authored Lua content
}
```

The field flows into `<game>/game.config.lua` (auto-generated by
`gameconverter`, which already wraps `modinfo.lua` via `VFS.Include`), is
read by the sim at startup, and is broadcast to clients on the first
`GameInfo` message.

New games leave the field absent (defaults to `false`) and pay no bridge
cost beyond a predicted-not-taken branch per callout.

### What the bridge does

When the flag is set, every coord-touching Lua callout mirrors world `Z`
(and the equivalent matrix entries) at the language boundary. Heading
itself is left untouched: the same `u16` names the same visual rotation
in both frames, only its conversion to/from a direction vector needs
adapting.

**Server side** — [`rts/Lua/LuaCoordAdapt.h`](../rts/Lua/LuaCoordAdapt.h)
with branch-on-flag inline helpers:

| Helper                                  | Behaviour                                        |
| --------------------------------------- | ------------------------------------------------ |
| `LuaCoordAdapt::FlipZ(z)`               | `−z` when legacy, `z` otherwise                  |
| `LuaCoordAdapt::FlipVec(v)`             | mirror `v.z`                                     |
| `LuaCoordAdapt::FlipMatrix(m)`          | conjugate by `diag(1, 1, −1, 1)`                 |
| `LuaCoordAdapt::FlipCommandPositionZ(c)`| mirror `params[2]` of position-bearing commands  |

Callouts wrapped:

- `Spring.GetUnitPosition` / `GetUnitBasePosition` / `GetUnitDirection` /
  `GetUnitVectors`
- `Spring.GetUnitPiecePosition` / `GetUnitPieceDirection` /
  `GetUnitPiecePosDir` / `GetUnitPieceMatrix`
- `Spring.GetVectorFromHeading` (output `z`) /
  `Spring.GetHeadingFromVector` (input `z`)
- `Spring.CreateUnit` (input `z`)
- `Spring.SetUnitPosition` / `Spring.SetUnitDirection` (input `z`)
- `Spring.GiveOrderToUnit` / `GiveOrderToUnitMap` /
  `GiveOrderToUnitArray` (`params[2]` of position-bearing commands —
  `CMD_MOVE`, `CMD_ATTACK`, `CMD_PATROL`, `CMD_FIGHT`, `CMD_REPAIR`,
  `CMD_RECLAIM`, `CMD_RESURRECT`, `CMD_CAPTURE`, `CMD_LOAD_UNITS`,
  `CMD_UNLOAD_UNIT`/`UNITS`, `CMD_AREA_ATTACK`, `CMD_MANUALFIRE`, and
  build commands with `cmdID < 0`)

Plus the feature-side mirrors of the same `GetSolidObject*` helpers, so
`Spring.GetFeaturePosition` / `GetFeaturePieceMatrix` / … behave
identically.

**Client side** — closure-captured `flipZ` / `flipCommandPositionZ` in
[`client/src/core/lua-spring-api.ts`](../client/src/core/lua-spring-api.ts)
and the matrix flip helper in
[`client/src/core/lua-gl-bridge.ts`](../client/src/core/lua-gl-bridge.ts):

- `Spring.GetUnitPosition` / `GetUnitDirection` / `GetUnitVelocity` —
  output `z` mirrored.
- `Spring.GetHeadingFromVector` — input `z` mirrored, then computed
  against the RH `atan2(x, −z)` formula.
- `Spring.GetGroundHeight` / `GetGroundOrigHeight` / `GetGroundNormal` /
  `GetSmoothMeshHeight` / `IsPosInLos` / `IsPosInAirLos` / `IsPosInRadar`
  — input `z` mirrored (and output normal Z mirrored).
- `Spring.GetUnitsInRectangle` / `Cylinder` / `Sphere` — input bounds
  mirrored, rectangle bounds re-sorted post-flip.
- `Spring.GiveOrderToUnit` / `GiveOrderToUnitArray` / `GiveOrder` /
  `GiveOrderArrayToUnitArray` — `params[2]` mirrored for the same
  position-bearing command list as the server side.
- `Spring.SetCameraTarget` / `SetCameraState` (`pz` / `tz`).
- `Spring.MarkerAddPoint` / `MarkerAddLine` / `MarkerErasePosition`.
- `gl.Translate(x, y, z)` and `gl.Rotate(angle, ax, ay, az)` — axis `z`
  mirrored on the immediate-mode matrix stack.
- `gl.LoadMatrix(m)` / `gl.MultMatrix(m)` — conjugated by
  `diag(1, 1, −1, 1)`.

Heading values (`Spring.GetUnitHeading`, the `heading` field of unit
records, etc.) are passed through unchanged. The same integer means the
same visual rotation in both frames; only the heading↔direction-vector
conversions need adaptation.

## Migration guide for new games

A new game should leave `legacyCoordSystem` absent in its `modinfo.lua`
and author all of its Lua content directly in RH:

- A unit at `heading = 0` faces `−Z`. Place start positions, build
  templates, and any hand-tuned positions assuming this.
- `Spring.GetVectorFromHeading(0)` returns `(0, 0, −1)`, not `(0, 0, 1)`.
- Asymmetric piece offsets in `.config.lua` follow the model's RH frame:
  the left wheel of a tank sits at `offset.z = −5.9`, not `+5.9`.
- Build orders sent through `Spring.GiveOrderToUnit` pass build positions
  in RH; no Z negation required.

If you're porting LH content incrementally, the safe migration path is:

1. Set `legacyCoordSystem = true` in `modinfo.lua` to keep the existing
   widgets/gadgets running while you port other systems.
2. As individual scripts are reviewed and converted to RH, leave them
   under the same flag — the bridge is uniform across the corpus, so
   you can't run half-LH and half-RH inside the same game session.
3. Once every script is RH-native, flip `legacyCoordSystem` to `false`
   (or remove the field) and verify a clean run.

## Removing the bridge

When no game needs the legacy adapter any more, deletion is one
mechanical pass:

```sh
grep -r legacyCoordSystem
```

The grep finds:

- `CModInfo::legacyCoordSystem` and the `TryLoadGameConfig` pass that
  populates it (`rts/Sim/Misc/ModInfo.{h,cpp}`).
- The `GameInfo.legacy_coord_system` FlatBuffers field
  (`schemas/protocol.fbs`).
- The `Protocol::BuildGameInfo` argument and the periodic broadcast in
  `rts/server_main.cpp`.
- The helpers in `rts/Lua/LuaCoordAdapt.h` and every call site in
  `LuaSyncedRead.cpp` / `LuaSyncedCtrl.cpp`.
- The client mirror in `client/src/core/lua-spring-api.ts` and
  `client/src/core/lua-gl-bridge.ts`, plus the plumbing through
  `connection.ts` → `main.ts` → `lua-widget-manager.ts` →
  `lua-widget-worker.ts`.

At each site, drop the `Flip…` wrapping and inline the original value;
delete `LuaCoordAdapt.h` and the client equivalents; drop the field from
every `modinfo.lua` that still carries it. No widget-level metadata, no
gameconverter post-pass — the cleanup leaves no orphan state in game
content.
